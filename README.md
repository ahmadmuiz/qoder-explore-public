# Laras — Payment Reconciliation Control Room

Pilot deliverable for **Bank Cakrawala Nusantara (BCN)**. Laras matches incoming bank settlements to vendor invoices by **payment reference × amount**, queues duplicates and mismatches, and surfaces missing payments — with every exception backed by ledger, invoice and kuitansi evidence. A second, deal-level control reconciles **treasury, securities and corporate financing** (money market, repo, bonds, FX spot/forward/swap, IRS, loans, project and trade finance) against trade confirmations, custody statements and settlement cashflows.

Use case: *Payment records disagree; exceptions need manual checks.*
Pass criteria: **missing payments surface**, **re-import adds no duplicates**.

> **Synthetic pilot.** All counterparties, accounts, amounts, screenshots and credentials in this repository are fictitious. No production, customer or confidential bank data is included.

## Canonical pilot data

- 250 invoices, 237 ledger payments, 235 kuitansi, 8 stored documents.
- 228 exact matches, 4 provisional, 0 tolerance; coverage 91.2%.
- 22 open exceptions: 6 missing, 2 duplicate payments, 4 amount mismatches, 3 unallocated, 4 nominal variances, 2 orphan kuitansi, 1 duplicate kuitansi.
- Value at risk Rp 7,275,356,500; matched value Rp 53,219,086,000.

Sample CSVs live in `02-source/backend/data/sample/`. Re-importing any of them is rejected by SHA-256 checksum; `ledger_late_arrival.csv` clears INV-2026-0018 and lifts coverage to 91.6%.

## Treasury dataset

`npm run seed:treasury` (deterministic, seed 2026-11-19) produces:

- Default book: 15,646 deals across 13 products (1,200 base deals each plus 46 sampled duplicates), 29,942 cashflow legs, 43,136 supporting documents and 39 counterparties; 94.6% full matches and 1,049 open breaks.
- Load-test book (`TREASURY_PER_CATEGORY=5000`, ~8s seed): 65,214 deals, 124,821 cashflow legs, 179,813 documents, 94.3% full matches, 4,626 open breaks (1,010 critical, 2,841 high, 775 medium) and Rp 61,735T notional; the Treasury page stays responsive (summary 173 ms, deal list 63–94 ms, accrual 0.9 s cold / 11 ms warm).
- Booked cashflows, reconciliation expectations and the accrual script all derive from one `expectedLegs` definition, so a leg is checked on amount (5×10⁻⁵ relative tolerance) and value date.
- The **Treasury** page shows coverage by product, the deal register, the break queue, a per-deal drawer with documents and legs, and a **Month-end accrual** tab with the balanced double-entry journal and per-deal calculation formula. CSV export: `/api/treasury/accrual/export?period=YYYY-MM`.
- Reference deals with full terms, cashflow legs, month-end accrual formulas and the resulting journal are generated by `npm run showcase:treasury` into [TREASURY-WORKED-EXAMPLES.md](01-documents/TREASURY-WORKED-EXAMPLES.md).
- Scope, conventions, rules, break taxonomy and the 12 sampling scenarios are in [TREASURY-SAMPLING.md](01-documents/TREASURY-SAMPLING.md).

## Core behavior

1. **Normalize** payment references (uppercase alphanumerics) and match by reference + amount: EXACT (100), TOLERANCE (98), PROVISIONAL (72), with an invoice-number + amount + currency fallback.
2. **Queue** anomalies with severities and signed deltas: MISSING_PAYMENT, DUPLICATE_PAYMENT, AMOUNT_MISMATCH, UNALLOCATED_PAYMENT, NOMINAL_VARIANCE, ORPHAN_RECEIPT, DUPLICATE_RECEIPT.
3. **Resolve** with codes (CONFIRMED_DUPLICATE, REFUND_INITIATED, ADJUSTED, EVIDENCE_ACCEPTED, WRITTEN_OFF, FALSE_POSITIVE, ESCALATED); notes are mandatory and resolutions above Rp 2,500,000 require a supervisor.
4. **Auto-clear** on re-run when the underlying condition disappears — resolution code AUTO_CLEARED.
5. **Stay idempotent**: file checksum blocks replay, row hashes skip overlapping statements, batch history records every attempt with zero inserts.
